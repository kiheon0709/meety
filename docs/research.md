# 조사와 측정 기록

미티를 만들면서 무엇을 조사하고 직접 쟀는지, 그 결과로 무엇을 정했는지 남깁니다. README에는 요약만 있고, 표와 측정 조건은 여기에 있습니다.

측정 수치는 모두 Apple M3 Max 맥북에서 직접 잰 값입니다. 실제 사람 목소리가 담긴 시험 녹음은 저장소에 없어서, 표의 숫자 중 일부는 이 저장소만으로 다시 잴 수 없습니다.

## 1. 언제 말해야 하나: 논문 조사

회의에서 먼저 말하는 AI는 말 자체보다 때를 잘못 잡아서 거부당합니다. 그래서 턴 전환과 능동형 에이전트 연구를 먼저 읽었습니다.

| 연구 | 내용 | 미티에 반영한 것 |
| --- | --- | --- |
| [Levinson & Torreira 2015](https://www.frontiersin.org/journals/psychology/articles/10.3389/fpsyg.2015.00731/full) (Stivers 2009 데이터 재인용) | 사람은 말을 받을 때 간격이 대부분 0~200ms, 한국어 평균 약 182ms | 지목받지 않은 참석자는 사람이 받는 자리를 다툴 수 없음. 먼저 꺼내는 말은 아무도 받지 않은 침묵에서만 |

| [Controlling AI Agent Participation](https://arxiv.org/abs/2501.17258) (IUI 2025) | 브레인스토밍 참가자 18명 중 13명이 부를 때만 오는 AI를 선호, 불만은 말이 길고 잦은 것 | 얼마나 나설지 팀이 정하는 참여도 다이얼, 짧은 말투 |

| [Bringing Everyone to the Table](https://arxiv.org/abs/2508.08242) (CSCW 2026) | AI 진행자로 전원이 말한 그룹이 39~47%에서 61%로 늘었지만, 정답 선택률은 차이가 없고 산만하다는 평가는 더 높음 | 미티가 "결정을 더 좋게 만든다"고 주장하지 않음. 실사용 평가는 앞으로 할 일 |

**상용 제품 조사** (2026년 10월): Zoom, Microsoft Teams, Google Meet, Otter, Fireflies, Granola 등은 대부분 회의를 받아 적고 끝난 뒤 요약하거나 부를 때만 답했습니다. 회의 중에 지난 결정과 어긋나는 말을 짚는 제품은 찾지 못했습니다.

## 2. 무엇으로 만들까: 음성 프레임워크와 실시간 음성 모델

공개 문서와 공개 벤치마크로 비교했습니다. 직접 돌려 잰 것은 아닙니다.

| 후보 | 조사 결과 | 판단 |
| --- | --- | --- |
| OpenAI Realtime, Gemini Live | 말 끝에서 첫 소리까지 공개 측정값 약 1.4~2.2초(영어). 화자 구분이 없고, 회의 소리를 통째로 보내면 비용이 커짐 | 안 씀. 언제 말할지와 네 명 구분은 어차피 우리 몫 |
| Pipecat | Smart Turn v3.2 포함, 라이선스 BSD. 옮기면 화자 구분과 두뇌 연결을 다시 짜야 함 | 프레임워크는 옮기지 않고 Smart Turn만 가져옴 |
| LiveKit Agents | 좋은 턴 감지와 추임새 구분이 클라우드에 묶임 | 안 씀 |

공통 한계: 조사한 프레임워크는 모두 세션당 사용자 한 명을 전제로 합니다. 마이크 하나로 네 명을 듣는 일은 직접 만들어야 해서, 음성 서버를 직접 구성했습니다.

## 3. 먼저 말하기: 설계를 다시 짠 과정

1. **첫 방식**: Inner Thoughts처럼 발화 후보마다 점수를 매겨 문턱을 넘으면 말하게 했습니다.
2. **실패**: 실제 회의 녹음 71분을 끝까지 돌려 보니 **한 번도 먼저 말하지 않았습니다.** 거르는 단계가 너무 보수적이었습니다.
3. **지금 방식**: 후보를 모아 두었다가 주제가 바뀌거나 대화가 멈춘 순간에만 고릅니다. 기본 선택지를 "가만히"로 두고, 쉬는 시간, 최근 말 비중, 침묵 길이를 코드가 확인합니다. 늘어난 비용은 회의 1시간에 약 0.28달러입니다.

같은 71분 녹음에서 반대 실수도 찾았습니다. 처음에는 결정을 설명하는 말 하나를 결정과 어긋난다고 잘못 짚었습니다. 안 끝난 말과 부정하는 말은 확인을 거친 뒤에만 말하도록 고쳤고, 그 회의의 받아쓰기 562마디를 두뇌에 다시 넣어 잘못 끼어드는 일이 없어진 것을 확인했습니다.

## 4. 음성 인식(STT) 비교

| | mlx-whisper turbo (로컬, 마디 단위) | Soniox stt-rt-v5 (클라우드) | WhisperLiveKit SimulStreaming (로컬 스트리밍) | sherpa-onnx 한국어 zipformer (로컬, CPU) |
| --- | --- | --- | --- | --- |
| 글자 오류율, 합성 대본 4개 (41마디) | 2.4~4.4% | **0.6~2.2%** | 4.8% (대본 1개만) | 40% (대본 1개만) |
| 글자 오류율, 실제 1:1 목소리 13발화 | 12.2% | **9.4%** | | |
| 말 끝 → 확정, 중앙값 / p90 (실제 1:1) | 664 / 858ms | **556 / 834ms** | | 1110ms (8발화) |
| 받아쓰기 시간 (실제 1:1) | 268ms | **207ms** | | |
| 중간 결과 간격 (실제 1:1) | 832ms | **352ms** | 0.1초마다 | 0.1초마다 |
| 앞 중간 결과를 고쳐 쓴 비율 (실제 1:1) | 56.9% | **1.3%** | | |
| "두 번 연속 같으면 믿기" 규칙의 틀린 글자 | 2.7% | **0%** (규칙 없이 믿으면 18.4%) | | |
| 그때 음성 합성 첫 조각 | 156ms | 134ms | **908ms** | |
| 비용 | 0 | 시간당 약 0.12달러 | 0 | 0 |

읽는 법과 판단은 이렇습니다.

- **정확도와 안정성은 Soniox가 가장 좋았습니다.** 실제 1:1의 정답은 whisper 결과를 고친 것이라 whisper에 유리한 기준인데도 Soniox가 낮았습니다.
- **로컬 스트리밍은 GPU 다툼이 문제였습니다.** WhisperLiveKit은 GPU를 내내 잡아서 같은 맥의 음성 합성 첫 소리가 0.16초에서 0.91초로 늦어졌습니다. 마디마다 whisper를 돌리는 방식은 GPU를 마디 끝에만 잠깐 써서 괜찮았습니다.
- **기본은 Soniox, 안 되면 whisper로 정했습니다.** 연결이 안 되거나 늦으면 그 마디는 whisper가 받아 적어 회의가 글자 없이 멈추지 않습니다. 키를 비우면 음성이 노트북 밖으로 나가지 않습니다.
- **다른 사람 목소리는 클라우드로 보내지 않았습니다.** Soniox로 보낸 실제 녹음은 동의한 본인 1:1 녹음뿐이고, 네 명이 나오는 실제 회의 녹화(11분 50초)는 로컬 whisper로만 쟀습니다(글자 오류율 5.3%).
- **값을 다시 잰 일도 있습니다.** 처음 잰 Soniox 오류율 24.4%는 연결 코드 버그 탓이었습니다. 확정 요청마다 글자 조각의 시각이 뒤로 밀려서, 말 끝 글자가 다음 마디로 넘어가고 있었습니다.

| | 침묵 500ms (예전) | Smart Turn v3.2 + 침묵 200ms (지금) | Soniox 자체 말 끝 |
| --- | --- | --- | --- |

| 말 중간에서 끝났다고 봄, 합성 대본 41마디 | 0 | 0 | **9개** |
| 말 중간에서 끝났다고 봄, 실제 1:1 | 0 | 0 | 28개 중 **3개** |
| 실제 회의 71분(한 사람이 길게 설명) | 기준 | 확정의 18%가 0.3초 빨라짐, 짧은 쉼에서 분당 1.3번 더 끊음 | 재지 않음 |

클라우드 엔진의 말 끝 판단이 더 늦고 문장 중간에서 더 끊겼습니다. 그래서 말 끝은 음성 서버가 Silero VAD와 Smart Turn으로 정하고, Soniox에는 그 순간 확정 요청만 보냅니다. Smart Turn은 대화에서 효과가 크고, 혼자 길게 말할 때는 효과가 작습니다.

## 6. 음성 합성(TTS) 비교

오픈소스 한국어 모델 5종을 같은 대사 4개로 비교했습니다. "첫 소리"는 합성을 시작해 처음 들리는 소리가 나올 때까지, RTF는 합성 시간 ÷ 소리 길이입니다.

| 모델 | 첫 소리, 중앙값 | RTF | 메모리 | 잘못 읽음 (4문장 중) | 라이선스 | 판단 |
| --- | --- | --- | --- | --- | --- | --- |
| Supertonic-3 (8단계) | 725ms | 0.20 | | 0 | 코드 MIT, 모델 OpenRAIL-M | 스트리밍이 안 됨. 예비 엔진으로 둠 |
| **Qwen3-TTS 1.7B** | **136ms** (튜닝 후 112ms) | 0.33 | 6.7GB | 1 | Apache-2.0 | **채택** |
| VoxCPM2 2B | 약 2500ms | 0.73~0.86 | 6GB | 1~2 | Apache-2.0 | 느림 |
| Chatterbox 다국어 | 1208ms | 0.36 | 2.3GB | 1 | MIT | 스트리밍이 안 됨 |
| Fish Audio S2 Pro | 약 630ms | 1.45 | 13.3GB | 0 | 비상업만 | 실시간보다 느리고 쓸 수 없는 라이선스 |

- 설치 문제로 MeloTTS, CosyVoice를 못 돌렸고, XTTS-v2는 비상업 라이선스라 뺐습니다.
- **빠르기만으로 고르지 않았습니다.** 직접 들어 보니 목소리가 "느리고 축 처진다"는 평가가 나와서, 말투 지시와 재생 속도를 바꾼 후보 10개를 다시 만들어 들어 보고 골랐습니다.
- **문장마다 말투가 들쭉날쭉한 문제**는 온도(0.9→0.5), top_k(50→20), 문장마다 같은 씨앗(7)으로 줄였습니다. 지금 설정은 Sohee 프리셋, 재생 속도 1.2배입니다.
- 재생 속도는 처음에 ffmpeg로 만들었지만, 파이프가 입력을 0.17초씩 붙잡아 문장 첫머리가 늦었습니다. 조각을 따로 늘이면 이음매가 튀어서, 문장 하나 동안 상태를 들고 있는 WSOLA를 직접 구현했습니다(`voice/tts_stretch.py`).
- 합성한 소리를 다시 받아 적어 잘못 읽는 곳을 찾았습니다. 짧아서 뭉개지는 문장과, 에코만 들어와도 끼어들기로 잡히는 맞장구 문장은 뺐습니다.

## 7. 지연 측정

음성 서버가 한 턴마다 말 끝 판정, 받아쓰기, 판단, 목소리 첫 조각, 재생 시작을 기록합니다. 단계별 중앙값은 이렇습니다(실제 1:1 녹음 재생, 판단은 800ms로 흉내).

| 말 끝 판정 | 받아쓰기 | 판단 | 목소리 첫 조각 | 재생 시작 | 말 끝 → 첫 소리 |
| --- | --- | --- | --- | --- | --- |
| 338ms | 264ms | 803ms (흉내) | 154ms (캐시 1~4ms) | 1ms | 1690ms |

가장 큰 덩어리는 모델 첫 글자입니다. 이것은 실시간 음성 모델로 바꿔도 피할 수 없어서, 즉시 나오는 채움말, 빠른 목소리, 짧은 침묵 대기를 함께 썼습니다.

개선 수치와 측정 조건은 [README의 지연 최적화](../README.md#지연-최적화) 절에 있습니다.

## 8. 팀 자료 검색

- **벡터 DB 없이 시작했습니다.** BM25만으로도 숫자, 고유명사, 받아쓰기 흔들림("미띠", "젯슨")에 강했고, 임베딩은 뜻만 같은 말을 잡으려고 더했습니다.
- **한국어라 글자 2-gram을 씁니다.** 띄어쓰기를 지우고 두 글자씩 잘라 "강도는/강도를", "세 단계/세단계" 차이를 견딥니다.
- **두 결과는 RRF(k=60)로 합칩니다.** 각각 상위 20개를 봅니다. 임베딩은 질문 한 문장에 중앙값 1.9ms라 회의 중에 부담이 없고, 50ms를 넘으면 그 검색은 BM25만 씁니다.
- **평가**: 질문 120개 중 108개에서 상위 3개 안에 정답이 있었습니다.
- **자료와 결정을 나눈 이유**: 문서는 낡습니다. 실제로 예전 문서에 뒤집힌 원칙이 그대로 남아 있는 것을 시험 중에 발견했습니다. 자료에 적힌 내용으로 사람을 단정해 짚으면 낡은 문서를 근거로 사람을 탓하게 되므로, 자료와 어긋나면 질문으로만 묻습니다.

## 9. 먼 거리 음성 인식 (한계)

네 명이 한 회의실에서 쓰는 환경은 거리, 울림, 소음을 합성한 녹음으로만 쟀습니다. 노트북에서 2m 떨어지고 울림이 있으면 글자 오류율이 5.3%에서 16.3%로 올라, 노트북을 테이블 가운데 두기를 권장합니다. 실제 회의실 측정은 앞으로 할 일입니다.
